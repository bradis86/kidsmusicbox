# API and trust boundaries

All JSON mutations use strict Zod schemas. Unknown fields and malformed values return 422. Parent/child cookie mutations require the corresponding session's `X-CSRF-Token`; explicit cross-origin requests are rejected. Read the token from the matching session endpoint. Browsers never receive MA credentials. Passwords use salted scrypt; SQLite contains token hashes rather than raw session cookies.

| Scope                 | Routes                                                                                                    | Authority                                                                                 |
| --------------------- | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Health                | `GET /api/health`                                                                                         | No credentials; app liveness only, not MA/player readiness                                |
| Parent authentication | `GET /api/auth/session`, `POST /api/auth/setup`, `/login`, `/logout`                                      | Setup requires a one-time server-side code; logout requires parent session + CSRF         |
| Child pairing         | `POST /api/admin/pair`, `/revoke-devices`                                                                 | Parent session + CSRF; pairs current browser only or revokes all child sessions           |
| Approved child data   | `GET /api/child/state`, `/collection/:id`, `/events`                                                      | Paired child cookie                                                                       |
| Child commands        | `POST /api/child/playback`, `/heartbeat`                                                                  | Paired cookie + child CSRF; no arbitrary URIs or player assignment                        |
| Library and tracks    | `GET /api/admin/library?search=&offset=`, `/search?search=`, `/tracks?id=`                                | Parent session; parent browses before approving an ID                                     |
| Approvals             | `POST /api/admin/collection`, `PATCH/DELETE /api/admin/collection/:id`, `PUT /api/admin/collection/order` | Parent session + CSRF                                                                     |
| Settings              | `GET/PUT /api/admin/settings`                                                                             | Parent read; mutations require CSRF                                                       |
| Status                | `GET /api/admin/state`, `/devices`, `/logs`, `/events`                                                    | Parent session                                                                            |
| Parent playback       | `POST /api/admin/playback`                                                                                | Parent session + CSRF; uses same approval and bedtime policy as child                     |
| Parent display        | `POST /api/admin/screen`                                                                                  | Parent session + CSRF; `{mode: "auto" \| "on" \| "off"}`                                  |
| Artwork               | `POST /api/admin/artwork`                                                                                 | Parent + CSRF, binary PNG/JPEG/WebP body, max 3 MB / 16M pixels; reencoded to WebP        |
| Artwork reads         | `GET /artwork/:source/:id`                                                                                | Parent or paired child, validated known IDs; MA source must come from discovered metadata |
| Mock lab              | `POST /api/admin/mock/connection`                                                                         | Parent + CSRF, mock mode only                                                             |
| HA automation         | `POST /api/automation/screen`                                                                             | Dedicated bearer token; screen mode only                                                  |

Playback bodies are `{action:"start", collectionId:"approved-id", trackId?:"approved-track-id"}`, `{action:"volume",volume:0..100}`, or `{action:"play"|"pause"|"stop"|"next"|"previous"}`. Actual requested volume is capped by saved settings. Mutations are serialised at the service boundary to keep order/policy/playback changes consistent.

Admin content patches can change `displayName`, `artworkOverride` (an uploaded local reference or null), and `hiddenTrackIds`. Hidden IDs must exist in the resolved item. Reordering requires exactly the current collection IDs without duplicates. Editing track exclusions stops the active collection before saving; removal records a pending stop if the player cannot be reached.

The app uses one logical device and shared approved collection. A pairing is a capability to operate that collection; anyone able to use a paired browser can use its child controls. Parent login is a separate cookie and permission. Pair on the device, log out of parent controls, and secure the OS kiosk. The simulator controls are parent-authenticated, while its embedded child UI has only the paired child's permission.

Sessions: parent 12 hours, child one year. Pairing survives a backend restart because sessions live in SQLite. Revoke pairings from Parent settings. Expired SSE clients are closed; browser EventSource retries automatically. A stale cached shelf may remain visible after pairing revocation, but read/mutation requests are rejected; the cache is presentation data, not authorisation.

The server serves restrictive security headers. The trusted-LAN deployment can use HTTP; use HTTPS and secure cookies when crossing less-trusted networks. MA's bearer token travels server-to-server, so use HTTPS on that link when it crosses an untrusted segment. Proxy buffering must be disabled for `/api/*/events`. No telemetry, remote fonts, cloud asset hosts or generic external URL/file fetch endpoints are included.

Parent Spotify links use `POST /api/admin/spotify/resolve` with `{link:"https://open.spotify.com/playlist/…"}`. Parent authentication and CSRF are required. The server validates and normalises the link, calls the backend's `resolvePlaylist`, and returns a preview. It does not approve automatically: the existing approval endpoint is the second step. The server never fetches arbitrary user-supplied URL hosts or follows shortened-link redirects. Mock mode returns a setup-required error, not invented metadata.

An optional `trackId` on a start command selects a specific track in the approved collection. Missing, foreign and hidden track IDs are rejected. The mock starts at that queue position; the real adapter uses documented `start_item` while keeping the explicit filtered track list. The child collection endpoint remains the sole source of selectable tracks.

Selected-song queue ordering is explicit: the chosen track is submitted first, then following tracks, then any preceding approved tracks. `start_item` also marks the chosen first song for MA’s shuffle handling. The server resolver only applies `start_item` positioning inside container expansion, so it is not relied on to reorder a list of track URIs. Both adapters use the same ordering.

`GET /api/admin/integration` requires a parent session and returns backend mode, connection status, compatibility version/schema, server URL, music-provider availability and playback targets. It never returns credentials. Target updates use the existing CSRF-protected settings endpoint.

Local native audio: `POST /api/child/audio/register` accepts the authenticated child's public `clientId` under CSRF/profile/device checks and claims its receiver; no browser pairing token or audio WebSocket is required. `GET /api/child/audio/state?clientId=...` returns only that receiver's native stream state. `GET /api/child/audio/stream/:generation` proxies buffered MP3 bytes under paired-session/client ownership and current-generation checks. `POST /api/child/audio/report` reports progress/end/error/boundary events, also bound to that receiver and generation. The long-lived MA token stays server-side. There is no `/audio/socket` or Sendspin transport. Parent settings may opt into `playbackMode=remote`; independent deployed players use local mode.

Start operations retain validated approved intent before the remote command. A lost acknowledgement triggers a state check rather than a retry; success is returned only when actual approved playback is confirmed. Queue track identity may match an equivalent provider URI supplied by MA metadata. The child snapshot uses the persisted approved collection id for that confirmed track.

Voice search: parent-only `GET /api/admin/voice` checks the local transcription service; paired-child/CSRF-protected `POST /api/child/voice/search` accepts raw WAV/WebM (max 5 MiB), and `/api/child/voice/matches` accepts corrected `{text}`. Responses contain transcript and approved-only result metadata; choosing a result still uses normal playback validation. Parent `voiceSearchEnabled` persists in settings; service credentials and private CA remain server-side. See [voice integration](voice-integration.md) for limits, privacy and cancellation.

## Parent catalogue search and standalone songs

`GET /api/admin/search?search=...` requires the parent session. It uses MA `music/search` with `library_only:false`, including albums, playlists and tracks from all connected music services (including the configured Spotify provider). It does not silently fall back to saved-library search. The query is1–120 trimmed characters;30 searches/minute per parent session, up to10 results per type, a15s MA deadline and20s Admin browser deadline. This MA API does not expose catalogue offsets; refine the query rather than presenting misleading Next-page controls. `/api/admin/library` remains saved album/playlist browsing with its existing offset behaviour.

Results enter the server's discovered-metadata catalogue; previewing/searching does not approve or start anything. `MusicItem.kind`/`ApprovedItem.kind` may now also be **track**. An approved standalone song is a one-track collection: parent preview resolves the exact song through `music/tracks/get`, validates its URI or equivalent provider mapping, and child playback queues only that approved song. Canonical MA library URIs are accepted when MA returns the requested Spotify identity in its provider mappings. Single-song data uses the existing JSON approval format, requiring no database schema change. MA provider instance IDs are case-sensitive: preserve the original URI scheme text rather than URL.protocol’s lowercase normalization, including for album/playlist previews. Hidden restrictions match all equivalent provider/library identities so later canonicalization cannot unhide a song. Parent rename/artwork/hiding/removal and normal bedtime/volume/session restrictions still apply. Voice matching sees only approved songs and does not gain catalogue access.

The Admin search defaults to catalogue search when text is entered, with a saved-albums/playlists option and local result-type filters. The child has no equivalent unrestricted search endpoint and cannot submit arbitrary Spotify track URIs as playback requests. No Spotify or MA credential moves to the browser.

The catalogue request limit is10 per type to match [Spotify's current search API range](https://developer.spotify.com/documentation/web-api/reference/search). Live MA requests with50 returned no Spotify album/playlist matches, while10 returned ten of each. This is catalogue coverage through MA, not identical personalized Spotify-app ranking, artist-profile browsing, podcasts/audiobooks or an exhaustive download of every match. Account/region/provider availability still controls playable results.

## Independent paired playback

With `INDEPENDENT_PLAYBACK=true`, child state/events, playback, reactions, audio ownership and heartbeat resolve their context from the authenticated pairing. The public audio client ID never chooses a device or MA target. State includes `independentPlayback`; personal state includes `preferencesVersion`, used to refresh open favourites after a shared-child preference change.

`GET /api/admin/profiles` adds `independentPlayback` plus each paired player’s `audioAssigned`, `online` and current `playback` summary. Parent/CSRF-protected `POST /api/admin/profile-devices/:id/stop` stops that device; `POST /api/admin/profile-devices/:id/release-audio` stops it and releases its reserved target. Release refuses to free a target when its remote stop is still pending. The legacy global parent playback endpoint returns 409 during independent playback; Admin directs parents to the individual paired-player controls. A third device trying to claim audio receives 409 and an actionable release-slot message. Read-only browsing never consumes a slot.

Child playback also accepts `{ "action": "shuffle", "enabled": true }` and `{ "action": "repeat", "enabled": false }`. Repeat maps to MA `all`/`off`. Both require the current authenticated device/profile and approved playback ownership. Successful acknowledged choices persist in context-local `queueModes`; `settings.shuffle`/`repeat` in child snapshots are the effective device settings. `device.name` in a child snapshot is the parent-assigned pairing/display name.

## Adult profile catalogue access

Parent profile creation accepts `kind: "child" | "adult"` (default `child`); profile editing accepts an optional `kind`. Only parent-authenticated routes can create/upgrade/assign adults. Existing profiles and newly paired devices retain child access.

- `GET /api/child/catalogue/search?search=<query>`: adult-assigned paired device only, query 1–120 characters, 30 searches/minute/IP, at most 30 results. Returns item wrappers with opaque `adult:<uuid>` IDs valid for 15 minutes, bound to device/profile/revision.
- `GET /api/child/collection/:id`: previews an adult result on its originating device, using the normal track format. Child profiles cannot preview or play these IDs. Arbitrary provider URIs are never accepted as playback collection IDs.
- `POST /api/child/playback`: existing `start`, transport, shuffle and repeat commands also accept a valid adult result. The server resolves the actual catalogue item; existing owner, CSRF, profile, volume, bedtime and stream-generation checks still apply.
- `POST /api/child/adult/lock` with `{}`: adult display only; stops/releases its playback, returns to its previously assigned child (or first available child), invalidates cached search results, and returns the updated child state. Parent settings are required to assign adult access again.

Catalogue routes require the same `X-Child-Profile`, `X-Child-Device` and `X-Profile-Revision` context headers as playback when multiple profiles exist. The normal child session cookie authenticates a paired display; its server-side assigned profile determines catalogue access. Voice matching/transcription uses catalogue search for adults and approved-only matches for children. Adult favourites may include unapproved music, without changing the children's approvals.

## Browser self-registration

`POST /api/child/pair` accepts JSON `{ "name": "Bedroom tablet" }` or `{}` without a parent login. It requires the parent account's initial setup to be complete. A new pairing returns HTTP201 with `{authenticated:true, csrf, personal}`, sets the normal HttpOnly/SameSite=Strict child cookie (Secure on HTTPS deployments), and assigns the first active child profile. The optional name is trimmed and limited to 60 characters. The endpoint rejects unknown fields, including requested roles/profile IDs/adult types. It never creates a parent session, starts audio or allocates an audio slot.

An existing valid child pairing returns HTTP200 with its existing context and CSRF token; it preserves the cookie, assigned profile (including an existing adult assignment), name and revision. Origin/Fetch Metadata checks apply and only JSON submissions are accepted. New creations are limited to 20 attempts per 15 minutes per observed source IP; valid existing pairings skip that creation limit. Access remains behind the existing private LAN/Teleport proxy restriction.

Revoking pairings returns open players to the setup screen when their heartbeat detects HTTP401. Users can explicitly register again; revocation is a registration reset, not a persistent device ban. Changing the assigned child/adult profile and other parent-only controls still requires parent authentication.

## Selection volume and loading feedback

Successful volume commands mark the context's optional `volumeChosen` flag. Explicit song/album starts preserve current volume when that player has an existing selection or chosen level, still clamped to the parent maximum; zero remains mute. First use follows startup volume. Automatic queue advancement already retains volume. This is selection-time behavior, not a guarantee across server restarts. The child shows the visual loading status only while start/resume/next/previous commands are pending, and clears it on completion/error.

## Sleep Music

Parents add individual songs to the separate Sleep Music list from a track preview in Browse library. `POST /api/admin/sleep-music` takes an already browsed `itemId` and a `trackId` resolved from that item. Parent-authenticated `GET /api/admin/sleep-music/sample` accepts the same query parameters or a saved `songId`. It uses Music Assistant's short clip service in the parent browser, without starting a player queue. `DELETE /api/admin/sleep-music/:id` removes a song and stops any session that selected it.

Child snapshots include `sleepSongs` when the profile has eligible songs and `sleepSession` while a session is active. A paired child selects one song using `{ "action": "start-sleep", "songId": "…" }` on the existing playback route. The hub queues just that song with repeat enabled and uses the next occurrence of **Sleep Music stops at** in the configured time zone as the stop time, even when the ordinary bedtime restriction is disabled. Sleep Music defaults to 07:00 and has its own setting in Admin → Settings & bedtime. Changing ordinary bedtime or the screen schedule leaves the Sleep Music cutoff alone. During bedtime the selected sleep song may play through its existing renderer. A child or parent can stop the session early. Sessions stop on hub restart and are never scheduled to start automatically.

During scheduled blanking, **Tap to wake for Sleep Music** in Admin → Settings & bedtime leaves a paired player with eligible songs touch-ready behind a black screen. A tap opens the Sleep Music picker for one minute at the device's usual brightness. While a song is playing, the crossed-out moon beside the footer volume slider stops it. The display blanks again after a successful start or stop, timeout, or **Darken screen**. The manual **Blank screen** override still uses the normal screen-off policy.
